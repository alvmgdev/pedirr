## MVP acceptance

Implementation and required verification are complete; see [the requirement-by-requirement review](mvp-acceptance.md). Final checks passed: 54 server tests, four integration programs, nine browser tests, type checking, production builds and dependency audit (zero known vulnerabilities). The deployed API, PostgreSQL, Redis and worker report healthy readiness.

A complete season is covered through HTTP approval, BullMQ and the native Sportarr HTTP adapter: all metadata pages are read, cancelled/inactive events are excluded, open seasons remain incomplete, closed imported seasons become available, and cross-season metadata is rejected before remote writes. Existing monitoring settings remain intact.

Known validation limits at MVP time: no real Sportarr installation or external email/Discord destination had been exercised. Since then Pedirr has run against a real Sportarr 4.1.11 installation (see [live validation](api-research.md#live-validation)); external email/Discord delivery is still unexercised. Native writes remain gated to the source-reviewed Sportarr 4.1 release line starting at 4.1.11. Upstream metadata quotas, update cadence and broadcast completeness are not guaranteed. No production-load benchmark or full manual accessibility certification is claimed.

- 2026-11-27: Plans as content packages (migration `202611270001_plans`). `Plan` holds a name and `allContent`; `PlanGrant` holds each Hub sport or league by canonical ID with its name; `User.planId` is optional and a plan with users cannot be deleted. - 2026-11-27: Catalog filtered by plan. `HubLeague` (migration `202611270002_hub_league_index`) indexes Hub's leagues with their sport; the worker job `league-index` refreshes it daily and at startup when stale, one page of 100 per job with a 4-second pause, under a Redis lock so overlapping runs never mix timestamps, and only a complete run removes leagues Hub no longer lists. `CatalogAccess` turns the viewer's plan into league and sport sets: search and the league list come from the index for users on a plan; single leagues, seasons and events are checked exactly (Hub is asked for a league not indexed yet); team events, the schedule and popular leagues are filtered. - 2026-11-27: Local schedule (migration `202611270003_hub_event_schedule`). `HubEvent` keeps Hub's events from 7 days ago to 14 days ahead with their league and teams and the item as served; the worker job `schedule-index` copies the whole window daily (and at startup when the last complete copy is missing or older than a day) and today and tomorrow hourly. Both background copies now share `pagedSync`: one page per job, a Redis lock per copy, one pace shared by every copy and sized to 30% of the Hub budget (so the daily, hourly and league copies never add up past it when they coincide), rows stamped with their write time so the cleanup of a complete run never removes rows written during it by another copy. `Schedule` serves `upcoming` for everyone (and owns the Hub fallback) (paged and filtered by plan in one query, cancelled and inactive events excluded) and adds teams and events to search for users on a plan; it is used only after a complete copy no older than two days, otherwise Hub answers. Verified with a new PostgreSQL and Redis integration program (`schedule.cjs`, with two deliberate breakages of the league and cancellation filters confirmed to fail it), all other programs, unit tests (background pacing), browser tests, and a run of the league index (1,539 leagues, 140 combat) and three schedule pages against the real Hub with a plan search and league list.

- 2026-11-28: Environment routing. `environmentPrefix` keeps the code of `/<code>/api/...` on the request and continues as `/api/...`, so every route serves the platform and resellers alike; the guard resolves the environment (the platform without a database lookup) and answers `TENANT_NOT_FOUND` for unknown codes. - 2026-11-28: Notifications per environment (migration `202611280002_tenant_notifications`). `NotificationSettings` takes an environment: the platform keeps the `notifications` setting and its secret contexts, so existing settings still decrypt; a reseller's live under `notifications:<id>` with secret contexts bound to its ID. - 2026-11-28: HTTP isolation suite (`http-isolation.cjs`). It boots the whole API, lists every route from the generated OpenAPI document and requires each to be classified as public, own account, content, environment data by ID, platform administration or reseller panel; an unclassified or vanished route fails it. With two resellers and the platform, each with an administrator and a client, it calls all platform administration routes as the reseller administrator, a reseller client, a platform user and anonymously (403/401), all reseller panel routes as the platform administrator, a client and a platform user (403/401), every route addressing reseller A's request, issue or client by ID from reseller B and the platform (404), and checks that requests, issues, popular leagues, clients and open-issue counts elsewhere hold nothing of A's. Removing the platform guard from one controller, or leaving a route unclassified, makes it fail.
- 2026-11-29: Plan search over the whole catalog. Hub's main search does not say which league a result belongs to, but its public TheSportsDB-compatible search does (events carry the league's short ID, teams its name), with no key and a published limit of 300 calls a minute. `HubProvider.searchWithLeagues` reads it (cached like other reads, under Pedirr's own budget), and `CatalogAccess.withinPlan` keeps the events and teams whose league the index places in the plan, leaving out unknown leagues; results join the league index and the local schedule, and Hub being busy only loses them. Searches end with a hint to find older events through their league, linking the leagues found. Verified with unit tests (URL encoding, parsing), the catalog integration program (plan filtering, unknown leagues, Hub failure), browser tests, and against the real Hub: a combat plan finds UFC 300 from 2024, an NBA plan finds 17 of 25 Lakers games and the team.
- 2026-11-29: Telegram notifications. One bot for the whole platform: its token is a platform setting, checked with `getMe` and encrypted under the `telegram.token` context; resellers can never set it. Each environment links one group or channel by posting a one-time code (`/link CODE`, 30 minutes, single use, a new one replaces the previous). The `telegram-poll` job runs every 5 seconds but reads `getUpdates` only while the `pedirr:telegram:pending` sorted set holds an unexpired code, so the bot is otherwise never contacted; each page of updates is handled before its offset is confirmed, and a lock keeps workers from reading the same updates. `TelegramChannel` sits behind `NotificationChannel` and follows Discord's routing (the platform's chat hears everything, a reseller's its own people), always with the platform's token; without it no Telegram delivery is planned. Errors carry codes only, never the token.
- 2026-11-27: Recovery of the background copies. An upgrade rehearsal from 1.1.0 during a Hub slowdown showed that a copy failing on its first page kept its two-hour lock, so retries and later runs were skipped, and that the daily copies waited a day after a failure. `pagedSync` now releases the lock when the first page fails and accepts a `due` check asked only when a run would start; the league index records its completion in `index.leagues` (a copy cut short stays due), and the league index and whole schedule are checked every hour (`INDEX_CHECK_EVERY_MS`) and copied when their last complete copy is a day old. Verified by the catalog and schedule integration programs with mutation checks, and in the rehearsal stack against the slow Hub.
